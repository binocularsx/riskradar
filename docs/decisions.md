It is never presented as bank engagement. | LOCKED |

| 19 | Case subject vs baseline subject | **They are different objects.** D13a's subject was silently defined as the *account*; a core banking identity hierarchy is customer-first (one CIF, many accounts). An ATO draining a victim's current, savings and domiciliary accounts would have opened **three cases for one incident** — the exact failure correlation exists to prevent. **Amends D13a: the subject of a case is `subject_token` (the customer). The subject of a behavioural baseline is `account_token` (the account).** | LOCKED |
| 19a | Token set | Four one-way HMAC-SHA256 tokens with the pepper, all deterministic: `subject_token` (customer), `account_token` (sender account), `beneficiary_token` (beneficiary account), `beneficiary_subject_token` (beneficiary customer, intrabank only, nullable). **D9c and D9d are unchanged** — nothing is reversible, the token still travels. Cost today: one column and one HMAC call. Cost in Week 4: reworking correlation, cases, features and every alert already written. | LOCKED |
| 19b | Simulator consequence | The simulator must model **customers who own multiple accounts**, not a flat list of accounts. Without this, `subject_token` and `account_token` are 1:1 in every generated row, the distinction is untestable and the column is decorative — the same criticism levelled at the rejected dataset in D10e. Owner: IRE, Week 2. Also improves the ATO typology: compromise a *customer*, drain across their accounts. | LOCKED |

| 20 | Event source layer | **Risk Radar consumes the channel and switch layers. The core banking system is an enrichment source, not an event source.** A ledger records postings — it has no device fingerprint, no IP region, no reliable channel, no merchant category, and **no declined authorisations**. Half of the canonical event in PRD §6.1 does not exist at the core and never did. Detection at the ledger is detection after the money has moved; the channel and switch layers are the only ones that see an event before authorisation, which is also the only place D7's enforcement seam could ever connect. | LOCKED |
| 20a | Typology observability | Recorded so the claim is never overstated in a defence: **mule fan-out** is fully observable at the core; **account takeover** only partially (the extraction posts; the compromise, device change and reconnaissance are not financial transactions); **card testing** barely (declines never post, approvals arrive as next-day settlement). All three stay in scope — they are synthetic in v1 and need no source system. | LOCKED |
| 20b | Core-derived enrichment features | Four features grounded in a real core data model rather than invented: `account_age_days` (mule fan-out), `dormancy_status` (ATO), `product_type` (baseline segmentation), `origin_sol_id` (coarse geography without a raw IP — NDPA-friendly). This is the concrete, defensible answer to "what did knowing the core system actually buy you". | LOCKED |
| 20c | Enrichment must not be a label proxy | Extension of D10a to our own generator. If the simulator sets `dormancy_status = DORMANT` only on ATO victims, dormancy **is** the label, the model learns a one-column shortcut, and D10b's held-out evaluation is worthless. **Rule: enrichment attributes are drawn from population distributions before any fraud process is assigned. A fraud process may _select_ on them; it may never _set_ them.** | LOCKED |

| 21 | Transaction outcome | **The canonical event gains `auth_result` (`APPROVED` / `DECLINED` / `FAILED` / `REVERSED`) and `decline_reason`.** Every field in the original §6.1 described a transaction that succeeded, so the event could not represent an *attempt*. This made **card testing unrepresentable** (D17 defines it as authorisation probes, which are predominantly declines — a third of the held-out evaluation in D10b rested on a typology the schema could not encode), made **ATO limit-probing invisible**, and made **reversals count as money moved**, double-counting value in every velocity sum. | LOCKED |
| 21a | Features split by outcome | `riskradar.features` filters every value-summing feature to `APPROVED`, and gains `failed_attempts_1h` and `decline_rate_24h` as first-class features. Changing the shared package (D15) **before** the equality test exists is far cheaper than after. | LOCKED |
| 21b | Declines are features, not automatically alerts | A probing burst is decline-heavy; routing declines straight to the alert path would blow past the alert budget in D11d. Declines feed features by default; promotion to an alert is the policy layer's decision like any other. | LOCKED |
| 21c | Ledger-leg invariant (resolves CB-1) | A core posts double-entry — one transfer becomes a sender debit, a settlement credit, a fee debit and a tax debit. Treating legs as events would make one transfer look like four transactions inside the velocity window, firing `VELOCITY_BURST_24H` on bank fees. **Under D20 Risk Radar never sees legs**, because the channel layer emits one event per customer action. Recorded as an invariant for any future core adapter: **one event is one customer-visible movement of value, never a ledger leg.** | LOCKED |

| 22 | Account context: stamped, not joined | **`product_type`, `origin_sol_id`, `account_opened_at`, `last_activity_at` are stamped onto the event at the ingestion boundary and immutable thereafter.** A mutable `accounts` dimension still exists for the analyst UI baseline panel (FR-024) and cross-account subject lookup, but **`riskradar.features` never reads it.** Joining a mutable dimension breaks G4 — re-deriving a six-week-old decision would read *today's* dormancy and reproduce a different answer — and creates point-in-time leakage in training, where an account marked dormant *because of* the fraud carries that attribute backwards into every training row. | LOCKED |
| 22a | Facts, not derived values | Store `account_opened_at` and `last_activity_at`, **not** `account_age_days` and `dormancy_status`. A timestamp never changes; an age changes nightly. Deriving age and dormancy band from `occurred_at` at feature time is point-in-time correct **by construction**, in the pandas path and the SQL path alike, with no as-of join to get wrong. | LOCKED |
| 22b | Why the equality test cannot cover this | D15's equality test proves the two paths agree, not that both are right. If both join the mutable dimension, both are leaked identically and the test passes. **This property is enforced by schema shape, not by a test** — which is why it had to be decided before migration one. | LOCKED |
| 22c | The bill | One more table and one more resolution step in Chidera's ingestion path, on top of D19a. Accepted because a decision record that reproduces to a different answer defeats G4, one of the five stated goals. **Makes the D12d compensating cut overdue.** | LOCKED |

## Build decisions (2026-09-09)

Decisions the implementation forced. Each one was a real problem, not a preference.

| # | Decision | Answer | Status |
|---|---|---|---|
| 30 | No Docker, no PostgreSQL on the build machine | The machine had neither (only SQL Server Express). Three LOCKED decisions depend on Postgres *specifically* — `SKIP LOCKED` (D8a), `LISTEN`/`NOTIFY` (D14a) and the `audit_log` grant (D12c) — so downgrading the datastore would have quietly voided them. **Solved by running PostgreSQL 16.4 from the portable binary distribution** under `~/.local/pgsql` on port 55432, no installer and no administrator rights. `docker-compose.yml` still ships for parity; it is not the path the demo uses (D26: local only). | LOCKED |
| 31 | Migrations | **Numbered SQL files and a 150-line runner**, not Alembic. The schema has a hard requirement that one role owns the objects and a different role receives narrow grants (D12c); a runner that makes that visible on the page beats a framework that hides it. | LOCKED |
| 32 | What "immutable" means | 0002 forbade both UPDATE and DELETE on `decisions`/`alerts` with **statement-level** triggers. Two faults: a statement-level trigger fires even for a zero-row statement, and blocking DELETE on `decisions` made `transactions` undeletable through the FK cascade — foreclosing the retention policy in D27. **Corrected in 0005: immutability means "never silently altered", not "never removable".** UPDATE stays forbidden at row level; DELETE is allowed. The tamper-evidence claim is unaffected because it rests on `audit_log`'s **grants**, which nothing the application does can sidestep. | LOCKED |
| 33 | Correlation race | 0001 enforced "at most one open case per subject" with a partial unique index — **stricter than D13a**, which opens a *new* case when the window has expired. A case left open for three days should not silently absorb next week's incident. The window cannot live in an index predicate (`now()` is not immutable), so **the race is closed with `pg_advisory_xact_lock` keyed on the subject token** instead (0004). | LOCKED |
| 34 | Serialising the audit chain | The obvious approach — `SELECT … FOR UPDATE` on the tail row — is **unavailable precisely because the control works**: `FOR UPDATE` requires UPDATE privilege, and the application role deliberately has none on `audit_log`. A transaction-scoped **advisory lock** needs no table privilege, so the chain stays serialised without weakening the grant. | LOCKED |
| 35 | Training-path performance | `load_history_frame` masks the whole dataframe per row — O(n²) over a corpus, which at 600,000 transactions is not slow but impossible. The honest consequence would have been somebody writing a second, faster implementation of the features for training, which is **exactly the skew D15 exists to prevent**. Solved by adding an indexed history *source*, leaving the feature functions untouched, and extending the equality test to assert all **three** data-access paths agree. | LOCKED |
| 36 | Scoring throughput | First measurement: **6.6 TPS, p50 182 ms** — nowhere near NFR-001. Two causes, both fixed: (a) the ablation explainer made 13 separate single-row predictions per transaction, ~39 tree-ensemble evaluations deep in sklearn call overhead — **batched into one matrix**; (b) the ruleset and threshold set were re-read from the database on **every transaction** — **hoisted to once per batch**, which is still fast enough that a mid-batch retune lands within a second (the property FR-040 actually needs). Result: **57.6 TPS, p50 14 ms, p95 23 ms.** | LOCKED |
| 36a | Attributions only where they are needed | G3 requires attributions on **alerts**, not on every decision, and the overwhelming majority of decisions are ALLOW. Explaining all of them was pure cost. The decision record still stores the model version and the full feature snapshot, so an attribution for a non-alerting decision can be recomputed exactly whenever anyone wants one. | LOCKED |
| 37 | Frontend styling | **Hand-written CSS with design tokens, not Tailwind.** A deviation from the Implementation Plan's tool table, recorded rather than hidden: it removes a build-time dependency from the one machine the demo must run on (D26), and the console is a dense, dark, purpose-built surface where a utility framework earns less than usual. React, Recharts and Vite are unchanged. | LOCKED |
| 38 | Demo profile fraud rate | The `demo` simulator profile runs at ~2–4% fraud, **not** the 0.3% operating point of D23: a demo database needs cases in it. The honest figures come from the `training` and `reference` profiles, and the QA report says so in the same breath. | LOCKED |
| 39 | System-level held-out evaluation | `evaluate.py` measures the **model**; its most valuable finding is a failure — with card testing held out, the model catches **none** of it (0/57 incidents). That is not a footnote, it is the argument for D11's three layers. So `evaluate_system.py` measures **model + rules + policy** on the same held-out typologies. Published in full. | LOCKED |
| 40 | `scripts/totp.py` | A development convenience for demo rehearsal, documented as such. | 41 | Queue claiming | **Measured, not assumed.** Three workers drained a burst backlog no faster than one (241s vs 239s). The first alert in a batch held a global lock for the rest of it, serialising every worker and then deadlocking them; a deadlock rolled the transaction back, releasing the claim on unprocessed rows **while the loop kept going**, producing 77 duplicate-key violations in one run. **Replaced `FOR UPDATE SKIP LOCKED` held across a batch with a committed lease** (`UPDATE ... | 41a | Scaling claim | Three workers gave **1.3x**, not 3x. The remaining bottleneck is a single Postgres instance on the laptop the demo runs on. The honest statement: the lock contention is removed and the architecture scales horizontally; the measured slope on this hardware is 1.3x. The ceiling is not mapped, and the QA report says so. | LOCKED |
| 42 | SSE on Windows | psycopg's async mode refuses to run on asyncio's `ProactorEventLoop`, the Windows default — and the demo runs on Windows (D26). Rather than force `WindowsSelectorEventLoopPolicy` process-wide, the stream keeps a **synchronous** connection and hands the blocking `LISTEN` wait to a thread.
